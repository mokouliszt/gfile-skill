# gfile — ギガファイル便で共有する

claude.ai(Web/モバイル)のサンドボックスから、ギガファイル便にファイルをアップロードして共有URLを発行するskill。
`<skill>` は、このSKILL.mdがあるフォルダ(例: `/mnt/skills/user/gfile`)を指す。処理はすべて `<skill>/scripts/gfile.py` で行う。

## 絶対ルール

1. **ダウンロードキー無しでは使わない。** `upload` は `--dlkey` が必須で、キーの設定・確認に失敗したらアップロード済みファイルを自動で削除する。ブラウザ操作・curl・自作コードなど別経路でアップロードしない。スクリプトを書き換えてキー処理を外さない。
2. **機密情報は如何なる理由があってもアップロードしない。** 対象はAPIキー、トークン、パスワード、秘密鍵、OAuth認証ファイル(auth.json等)、`.env`、keystore、クラウドの認証情報など。`secret_guard.py` が拒否したものは、ユーザーが望んでも上げない。回避策(ファイル名変更、暗号化・パスワード付きアーカイブ、base64化・分割、スキャナの改変、別経路でのアップロード)を探さない。
3. **個人を特定しうる情報は、ユーザーの判断なしにアップロードしない。** 対象は本名、住所、電話番号、メールアドレス、生年月日、口座・カード番号、マイナンバー、顔写真、位置情報など。画像(スクリーンショット等)の中身も含む。
   - 検出したら、該当箇所を**すべて**ユーザーに伝えて、どうするか確認する。
   - **勝手にマスキング・削除・ファイル除外をしない。** ユーザーが具体的に指示したときだけ、その通りに加工する。
   - 常識的に見て明らかな誤検出は、伝えずに無視してよい(下の「仕分け」を参照)。
4. `/mnt/skills` 以下や `/mnt/transcripts`、`.ssh` `.config` などの認証情報ディレクトリからはアップロードしない(スクリプトも拒否する)。
5. ユーザーが共有を意図していないファイルを勝手にアップロードしない。

## いつ使うか

- **明示指示**: ユーザーがギガファイル便での共有を指示した → サイズに関係なく使う。
- **サイズ超過**: 成果物を渡す直前にサイズを確認する。`30,000,000` バイト(30MB)を超えるファイルは present_files で渡さず、このskillを使う(根拠: claude.ai公式ヘルプ「The maximum file size is 30MB per file for both uploads and downloads」)。
  - 30MB以下のファイルは従来通り present_files で渡す。
  - サイズ超過で使うときは「30MBを超えるのでギガファイル便で共有します」と一言添える。

## 手順

### 1. 機密情報チェック(通信なし・数秒)

```bash
python3 <skill>/scripts/gfile.py check <ファイルまたはフォルダ ...>
```

`secret_scan.ok` が `false`(終了コード2)なら、ここで止める。検出結果(値はマスク済み)をユーザーに伝え、正当な対処を提案する。

- 正当な対処は次の2つで、どちらもユーザーの了承を得てから行い、終わったら再チェックする。
  - 該当ファイルを除いて作り直す
  - 該当箇所を実際に取り除いたコピーを作る
- 誤検知に見えても、該当テキストを取り除くまでアップロードしない。

### 2. 個人情報チェック(バックグラウンドで実行)

OpenAI Privacy Filter(ローカル実行のPII検出モデル)、正規表現、画像メタデータ(GPS・作成者)、OCR(日本語+英語)で検査する。結果を報告するだけで、ファイルは一切変更しない。

- 初回はモデル(約0.9GB)のダウンロードと読み込みに30〜40秒かかる。
- 推論は1コアで毎秒100〜150トークン程度。
- 時間がかかるため、常にバックグラウンドで実行して進捗を確認する。

```bash
nohup python3 <skill>/scripts/gfile.py pii <パス ...> --json-out /tmp/gfile_pii.json --md-out /tmp/gfile_pii.md > /tmp/gfile_pii.log 2>&1 &
# 数十秒おきに確認。/tmp/gfile_pii.json ができたら完了
tail -n 2 /tmp/gfile_pii.log; ls /tmp/gfile_pii.json 2>/dev/null
```

`--json-out` に書かれた前回の結果が残っていることがあるので、実行前に `rm -f /tmp/gfile_pii.json /tmp/gfile_pii.md` しておく。

レポートで見る項目:

- `findings`: 検出結果。各項目に `category_ja`、`value`(検出文字列)、`locations`(パス・行またはページ・種別・前後の文脈)が入る。種別は text / office / pdf / ocr(画像内) / metadata / filename のいずれか。
- `images_for_visual_review`: **自分の目で確認すべき画像**(最大20枚)。`path` を view ツールで開き、次のものが写っていないか確認して、見つけたら検出結果に加える。OCRは画質や表記ゆれで読み落とすことがあるため、この確認は省略しない。
  - 実在の人物の氏名・住所・電話番号・メール
  - 実在の人物の顔
  - 身分証や書類
  - 車のナンバー
  - 自宅を特定できる景色・地図
- `images_not_visually_listed` が1以上のとき、または `model.used` が `false`・`model.not_model_scanned` があるとき(トークン上限超過)は、その旨もユーザーに伝える。
- `not_scanned`(バイナリ等で検査していないもの)も、件数が多ければ一言伝える。

### 3. 仕分け(明らかな誤検出だけ外す)

次のような**常識的に明らかな誤検出**は外してよい。

- コードの識別子・UIの文言・ファイル名の一般語
- 製品名・企業名・公共施設・駅名・市区町村名だけの地名
- 著名人や歴史上の人物
- 同梱しているOSSライブラリのライセンス表記の作者名
- 明らかなサンプル・ダミーデータ(example.com、「山田太郎」がテスト用だと文脈から明らかなもの等)
- バージョン番号・リリース日・タイムスタンプなど、個人に関係しない日付や数字

少しでも迷うものは外さずに伝える。
モデルが `secret`(秘密情報)と判定したものは、本物の認証情報らしければルール2として扱う(ユーザーが望んでもアップロードしない)。ハッシュ値・UUID・サンプル値など明らかに無害なものなら外す。

### 4. ユーザーへの確認(逆質問ツール)

**個人情報が残った場合**は、まず本文に該当箇所をすべて列挙する。自分の目視確認で見つけたものも含める。

- 1項目ごとに「種別 / 検出内容 / 場所(ファイル・行またはページ、「画像内」「メタデータ」等)/ 前後の文脈」を書く。
- 件数が30を超えるときは、本文に要約を書いたうえで、`/tmp/gfile_pii.md` を `/mnt/user-data/outputs/gfile_pii_report.md` にコピーして present_files で全件を渡す。このファイルには誤検出の候補も含まれる旨を添える。

続けて、選択式で質問できるツール(claude.aiでは `ask_user_input_v0`)を1回だけ呼び、次の3問をまとめて聞く。個人情報が残らなかった場合は質問1を省いて2問にする。

- 質問1「検出された個人情報をどうしますか?」
  - 選択肢: `このままアップロード`、`該当ファイルを除いてアップロード`、`中止する(自分で修正する)`
  - 細かい指示(「この行だけ消して」等)は自由入力で受け付ける。
- 質問2「保存期限は?(3/5/7/14/30/60/100日から選択。一覧にない日数は入力)」
  - 選択肢の例: `7日`、`14日`、`30日`、`100日(最長)`
- 質問3「ダウンロードキーは?(半角英数1〜4文字)」
  - 選択肢: `MMdd(今日の日付)` と `任意のキーを入力する`
  - MMdd は時刻ツール(`user_time_v0` 等)で取得したユーザーのローカル日付で作る。時刻ツールが無ければ会話の現在日付を使う。選択肢には実際の値を入れる(例: `1005(今日の日付)`)。
- ユーザーが依頼文で値を指定していた場合は、その値を各質問の最初の選択肢にする。

回答の扱い:

- ユーザーの回答なしに既定値で進めない。
- **このままアップロード** → 手順5へ進む(`--pii-reviewed` を付ける)。
- **該当ファイルを除いて** → 該当ファイル(アーカイブ内ならそのメンバー)を除いた入力を作り直し、手順1・2をやり直す。そのうえで、新しい結果をもとに改めて確認する。
- **中止** → アップロードしない。
- **修正の指示** → 指示された通りにだけ加工し、手順1・2をやり直す。
- 保存期限は 3/5/7/14/30/60/100 のいずれかのみ受け付ける。キーは半角英数1〜4文字のみ受け付ける。キー本文が無い・不正な場合は、逆質問ツールでもう一度入力を求める。キーなしで進めたいと言われても断る(ルール1)。

### 5. アップロード

```bash
python3 <skill>/scripts/gfile.py upload <パス ...> --lifetime <日数> --dlkey <キー> \
  --pii-report /tmp/gfile_pii.json [--pii-reviewed] --json-out /tmp/gfile_result.json
```

- `--pii-report` は必須。手順2と**同じパス**に対するレポートでなければ拒否される。ファイルを作り直したら手順2をやり直す。
- `--pii-reviewed` は、レポートに確認が必要な要素がある場合に必要になる。確認が必要な要素とは、検出結果、目視確認用の画像、モデル未使用、トークン上限超過のいずれか。
  - 付けてよいのは、次のどちらかの場合だけ。
    - ユーザーが手順4で「このままアップロード」を選んだ
    - 仕分けの結果すべてが明らかな誤検出で、目視確認でも何も見つからなかった
- 複数ファイルやフォルダは、まとめて1つのzipにしてからアップロードする(`--name` でzip名を指定)。
- 数百MBを超えるファイルは、手順2と同じく nohup でバックグラウンド実行し、`/tmp/gfile_result.json` ができるまで進捗を見る。

終了コード:

| コード | 意味 |
|---|---|
| 0 | 成功 |
| 2 | 引数・入力エラー |
| 3 | 機密情報で拒否 |
| 4 | ネットワークエラー |
| 5 | ギガファイル便の応答異常(仕様変更の可能性) |
| 6 | ダウンロードキーの設定・確認に失敗(ファイルは削除済み。削除できなかった場合はJSONのURLと削除キーを必ず伝える) |
| 8 | 個人情報レポートが無い・古い・未確認 |

プロキシ拒否(`x-deny-reason`)が出たら、claude.aiのネットワーク設定で次のドメインを許可するよう案内する。

- `gigafile.nu`、`*.gigafile.nu`(アップロード先)
- `huggingface.co`、`*.hf.co`(モデル)
- `github.com`、`raw.githubusercontent.com`(OCRデータ)

### 6. 報告(必須項目)

`/tmp/gfile_result.json` から、次の4項目を必ずすべて伝える。省略・伏せ字にしない。

```
ギガファイル便にアップロードしました。
- 共有URL: <url>
- 保存期限: <lifetime_days>日(<expires_on> まで)
- ダウンロードキー: <dlkey>
- 削除キー: <delkey>
ファイル: <file_name>(<size_human>、SHA-256: <sha256 先頭12桁>…)
```

削除キーがあれば誰でも削除できるので、共有相手にはURLとダウンロードキーだけを伝えるよう一言添える。アップロードしたファイル自体は present_files に渡さない。

## 削除

```bash
python3 <skill>/scripts/gfile.py delete <共有URL> --delkey <削除キー>
```

## トラブル時

ギガファイル便側の仕様変更が疑われるとき(終了コード5など)は、`references/protocol.md` を読む。調査中も絶対ルールは変わらない。
